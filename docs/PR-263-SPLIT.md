PR #263 — סנכרון `master` → `main` — הוא 1472 שורות ב-38 קבצים, ולכן נחסם.

GitHub Pages מוגש מ-`main`, וכל שדרוגי המחקר יושבים ב-`master`. שני הענפים
התפצלו ב-`27f6691`: `master` 12 קומיטים לפנים, קומיט אחד לאחור
(`0e614ac` = #150 — `CONTACT` אחד, טופס פיילוט בעברית, עותק לפרויקט במכתב

## איך פותחים כל מסירה

```sh
git switch -c sync/263-1-audio origin/main
git cherry-pick --allow-empty 897c1d3 fe307ac 5e7aa34 097a2d7 ed625a4
npm test
git push -u origin sync/263-1-audio
gh pr create --base main --title "sync(main): AudioContext משותף ונעילת שמע (1/7 של #263)" \
  --body "חלק 1 מתוך 7 של הסנכרון. Refs #265, Refs #263."
```

ושוב לכל שורה בטבלה הראשונה. שתי נקודות:

- **`--base main`** בכל אחת. אלה לא מסירות ל-`master`; התוכן כבר שם.
- `5e7aa34` הוא קומיט **ריק** (התוכן של #161 נחת כבר קודם) ו-`097a2d7` הוא
  שורת precache אחת. שניהם מופיעים במסירה 1 כדי שאף קומיט מ-#263 לא ייפול בין
  הכיסאות — ובשביל הריק צריך `--allow-empty`, אחרת ה-cherry-pick נעצר.

## מה נשאר אחרי שבע המסירות

`main` תחזיק את כל התוכן של `master`, ו-PR #263 אפשר לסגור עם תגובה שמונה
את שבעת ה-PR-ים. שימו לב לסדר: **קודם פותחים את השבעה, ורק אחר כך סוגרים את
#263** — סגירה מוקדמת מאבדת את ההקשר.

מה שהפיצול הזה **לא** פותר הוא הייחוס: גם אחרי שהתוכן זהה, `main` לא יהיה אב
קדמון של `master` ולהפך. זה נשאר בדיוק כפי שתואר ב-#264, והצעד האנושי שם
(`git merge -s ours --no-ff`) עדיין הדרך היחידה להפוך את זה לשושלת אחת. אם
בוחרים בדרך של #264 — מיזוג #263 כ-merge commit אחרי יישוב התוכן — הפיצול
הזה מיותר; שתי הדרכים מגיעות לאותו עץ, והשאלה היא רק אם רוצים לעבור דרך
ה-auto_merger או דרך מיזוג ידני.
